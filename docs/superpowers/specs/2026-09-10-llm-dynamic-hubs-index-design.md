# LLM-Generated Dynamic Wiki Hubs and Index

## Goal

Make orphan healing dynamic for blank and established vaults. The system must
use the configured LLM to create semantic hub pages when no suitable hub
exists, and must use the LLM to create the initial `index.md`. Existing hubs
and indexes must be reused rather than regenerated unnecessarily.

## Scope

This change covers:

- Dynamic discovery of category hubs from hub-page frontmatter.
- LLM generation of the first hub in a blank vault.
- LLM generation of a new hub when an established vault has an unmatched topic.
- LLM generation of `index.md` when the vault is first bootstrapped or its
  page structure changes.
- Safe validation, dry-run behavior, and deterministic fallbacks.
- Tests for blank-vault bootstrap, reuse, structural changes, and failures.

It does not make the LLM rewrite existing hub content, automatically repair
ambiguous broken links, merge duplicate pages, or rewrite stale claims.

## Hub Metadata

A semantic hub opts into discovery through frontmatter:

```yaml
---
type: concept
lint_hub: true
lint_keywords: [trade, trading, freqtrade, mt5]
lint_priority: 100
---
```

`lint_hub` is a boolean marker. `lint_keywords` is a non-empty list of
normalized matching terms. `lint_priority` is an optional integer; higher
values win when multiple hubs match, and the normalized relative path is the
deterministic tie-breaker. Malformed metadata makes a page ineligible as a
dynamic hub rather than failing the whole lint operation.

The resolver matches an orphan against its relative path, title, page type,
tags, aliases, and body. It scans only pages that are marked `lint_hub: true`
and whose files exist in the current vault. No semantic category paths or
keyword lists remain in Python source.

## Lifecycle

### Blank-vault bootstrap

The standard skeleton may already contain a basic `index.md`, so blankness is
determined by the absence of curated pages, not by the absence of `index.md`.
After the first meaningful page is written:

1. Collect the page's validated metadata and content.
2. Ask the configured LLM to propose a first hub, including a safe concept
   path, title, introduction, `lint_hub`, `lint_keywords`, and priority.
3. Validate the proposal and create the hub without overwriting any existing
   file.
4. Link the orphan page from the new hub.
5. Ask the LLM to generate `index.md` from the authoritative page manifest.
6. Validate the index links and persist it atomically.

Generated hubs and `index.md` are navigation roots. They are excluded from
ordinary orphan-healing recursion so the bootstrap cannot create hubs in an
endless loop.

### Established-vault writes

For each orphan-healing pass, existing dynamic hubs are considered first. If a
matching hub exists, the system reuses it and does not call the LLM for hub
generation. If no hub matches, the system supplies the orphan and a concise
manifest of existing hubs to the LLM, asks for a new hub, validates it, and
then links the orphan to it.

Existing hub content is never replaced by this flow. New orphan links may be
added to a hub's generated navigation section.

## Index Regeneration

The index is generated by the LLM only when it is missing during bootstrap or
when the vault structure changes. Structural changes are page creation,
deletion, rename, or a change to hub-discovery metadata. Ordinary edits to a
page's prose do not trigger index regeneration.

The LLM receives an authoritative manifest containing each page's canonical
relative path, title, type, aliases, tags, hub marker, and short summary. It
may organize sections and write descriptions, but it may not invent paths or
omit required pages. The validator rejects nonexistent links, links outside
the vault, malformed frontmatter, and duplicate canonical entries.

The index remains atomically written and retains the required index
frontmatter and navigation contract. A structural manifest hash (or equivalent
validated state) is stored so ordinary writes can skip the LLM call.

## LLM Contract and Failure Handling

LLM calls use the configured Hermes one-shot runtime already used by the
project's reflection layer. Generation requests must ask for structured JSON
with separate fields for the target path, title, body, keywords, priority, and
index sections. The implementation must validate and normalize the response
before any filesystem write.

If the LLM is unavailable, times out, returns invalid data, proposes an unsafe
path, or returns a duplicate hub, the original page write remains successful.
The system falls back to the deterministic generic index and existing generic
orphan hub behavior, and reports the generation failure in the operation
result/log without exposing credentials or raw prompt contents.

`dry_run` must perform discovery and return the proposed hub/index changes
without writing files. A normal fix is the only mode allowed to persist the
validated proposal.

## Persistence and Safety

- Use the existing write lock and atomic-write helpers.
- Never overwrite an existing page when creating an LLM hub.
- Rebuild the deterministic index or preserve the last valid index if LLM
  index generation fails.
- Keep source pages read-only.
- Keep generated navigation separate from editorial page content.
- Preserve current user changes in `lint.py`, `vault.py`, and tests.
- Make LLM generation injectable or monkeypatchable in tests; tests must not
  require a live model.

## Testing

Add tests that verify:

1. A blank vault's first write creates one validated LLM hub and an LLM index.
2. A later matching write reuses the existing hub without another hub call.
3. An unmatched topic creates exactly one additional hub.
4. Existing hub content is not overwritten.
5. Index generation occurs on page/hub structure changes but not ordinary prose
   updates.
6. Generated links and paths are validated, and invalid LLM output is rejected.
7. LLM failure preserves the page write and uses the deterministic fallback.
8. `dry_run` returns proposals without modifying the vault.
9. Generated hubs and the index do not reappear as orphan errors.

## Acceptance Criteria

- No semantic category keyword or hub path is hard-coded in the resolver.
- A blank vault becomes navigable after its first page write without manual hub
  or index creation when an LLM is available.
- Established vaults reuse existing hubs and only generate new ones for
  unmatched topics.
- The LLM index is regenerated only for structural changes.
- Every generated artifact is validated, atomically persisted, and covered by
  tests.
- LLM outages do not make ordinary page writes fail.
